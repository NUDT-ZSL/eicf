某临床试验数据管理团队需要从多个本地站点收集电子知情同意书（eICF）的签署事件。每个站点暴露一个本地 HTTP 仿真接口，返回分页的签署记录，字段包括受试者编号、站点编号、方案版本、签署时间（秒级 UTC 时间戳）、签署状态（signed/withdrawn）、记录修订号（非负整数）、内容哈希。站点之间时钟不同步，会重复投递，会对已签署记录做撤回或更正，且分页过程中集合可能变化，服务端可能返回 429/500、慢响应或截断的 JSON。团队要求构建一个增量采集与审计快照服务：能对多站点做并发抓取、按业务键去重、按确定顺序仲裁冲突、生成可校验的整库快照与版本化差异，并在采集中断后从持久化状态恢复而不重复也不丢失修订。所有站点服务由任务代码在 Windows 本地确定性启动，不需要外部账号或公网。当前是空白工作区，需从零创建项目。

任务环境与准备：
Windows 10/11，已安装 Python 3.11 与 pytest 8.x（可在联网准备阶段通过 pip 安装，运行阶段不联网）；不使用 Docker 或任何容器环境。
当前为空白工作区，任务执行前需自行创建项目目录、源码、配置样例与测试文件；不提供任何已有代码或数据附件。
所有仿真站点、样本记录、故障注入均由任务代码在本地确定性构造，端口由测试运行时动态分配并回传。
确认本机回环地址可用且防火墙不拦截本地监听端口；如需安装 pytest，应在任务开始前完成并校验版本。

请在本轮完成以下要求，并实际运行验证：
1. 实现多站点采集调度器：从 JSON 配置文件读取站点列表（站点编号、基址、页大小上限），对每个站点用服务端返回的 next_cursor 分页抓取直到 has_more 为 false；同一站点内分页串行，不同站点之间并发，任意时刻全局正在进行中的 HTTP 请求数不超过配置的全局上限。游标推进只能依赖服务端返回的 next_cursor，禁止以页计数或游标字符串比较作为终止条件；遇到服务端重复返回同一 next_cursor 时最多重取一次，仍重复则判定该站点异常并按第 6 条报告。
   验收：用自带脚本启动 3 个本地站点，站点 B 在第 2 页故意返回与第 1 页数据相同但 next_cursor 不同的页、在第 4 页返回与第 3 页相同的 next_cursor 一次后恢复正常；执行采集命令退出码为 0，审计库事件条数等于三站点真实记录并集；服务端记录的最大同时进行请求数不超过配置上限且大于 1（证明并发生效），日志显示每站点游标严格按服务端给的 next_cursor 推进。
2. 定义跨源去重键：业务主键只能由站点编号、受试者编号、方案版本、签署时间（秒级 UTC 整数时间戳）组成，不得包含采集批次、来源 URL、抓取时刻或内容哈希等字段；同一业务键的多次投递是同一条记录的不同修订，修订按记录修订号区分。
   验收：站点 A 与站点 C 对同一受试者、同一方案版本、同一签署时间各投递一条记录仅内容哈希不同；采集后审计库中该业务键只有一行主记录，修订表保留两条不同哈希的修订；另构造仅抓取时刻不同、业务键完全相同的两次投递，断言主记录仍只有一行且修订未因此增加。
3. 实现确定性的冲突仲裁：同一业务键存在多个修订时，按（记录修订号降序，内容哈希字典序升序，站点编号字典序升序）选出当前有效修订；status=withdrawn 若其修订号不低于任何 signed 修订则有效状态为 withdrawn，若存在修订号更高的 signed 修订则以该更高修订号为准。仲裁结果必须与采集顺序、并发交错、站点响应顺序无关。
   验收：用两种相反站点响应顺序各跑一次完整采集，导出当前有效视图的规范化 JSON（键排序、无空白差异），两次输出逐字节相同；构造 withdrawn 修订号 5 与 signed 修订号 7，断言有效状态为 signed；构造 withdrawn 修订号 7 与 signed 修订号 5，断言有效状态为 withdrawn；构造同修订号不同哈希两条记录，断言选中哈希字典序较小者。
4. 生成整库审计快照：快照目录含清单文件（版本号、记录数、每站点记录数、内容集合哈希、每站点采集水位）与全部当前有效记录的规范化 JSON 文件；写入必须原子化（先写临时目录或临时文件，全部就绪后替换），集合哈希对记录按业务键排序后逐条规范化计算，不受文件系统遍历顺序影响；替换前失败必须使旧快照保持完整可用。
   验收：连续生成两次快照，第二次清单与记录文件内容与第一次逐字节一致且集合哈希相同；通过测试注入参数使替换阶段抛出异常，断言旧快照目录仍可完整读取且不存在半成品文件；变更一条记录后重新生成，断言集合哈希变化且清单记录数正确。
5. 实现版本化增量快照与旧快照识别：每次快照记录单调递增版本号和本次采集水位（每站点最后 next_cursor 与已处理最大签署时间）；新快照须与上一版本按业务键匹配得出新增、修订、撤回三类差异，禁止依赖上一快照文件的记录行偏移或行号定位记录。
   验收：首轮采集生成快照 v1；再让站点 A 新增 2 条、对 1 条产生更高修订号更正、对 1 条产生更高修订号撤回，执行增量采集生成 v2；断言 v2 差异报告新增 2、修订 1、撤回 1；断言 v2 清单版本号为 2 且站点 A 水位前进；人为打乱 v1 记录文件中的记录顺序后重新生成 v2，断言差异结果与打乱前一致。
6. 实现采集中断恢复：采集过程中每完成一页即将该页修订与该站点已提交 next_cursor 在同一 SQLite 事务内提交；进程被 Ctrl+C 或可捕获异常中断后重启，必须从最后已提交的 next_cursor 继续，不重复写入已入库修订，也不跳过未抓取页；无法执行清理代码的强制终止不做有退出报告的保证，只允许依赖已提交的 SQLite 状态恢复。
   验收：在站点 B 第 2 页抓取后通过测试钩子抛出异常使进程退出，断言退出码为 2 且 stderr 输出业务错误码 E_INTERRUPTED；重启采集，断言站点 B 从第 2 页之后的 next_cursor 继续，最终审计库主记录数与不中断采集完全一致且修订表无重复行；再执行一次不经过 finally 清理的 Process.terminate() 强杀，重启后仅凭 SQLite 状态恢复出与不中断采集一致的主记录集。
7. 处理服务端异常链路：站点返回 429、500、响应体 JSON 截断或连接超时时，对有明确可重试信号的情况按有上限的退避重试（最多 3 次，间隔由配置给出且允许为 0），重试耗尽后把该站点标记为不完整并继续其他站点；不完整站点的部分数据不得进入被标为完整的快照，必须生成清单中 incomplete=true 并列出受影响站点的快照，且其他站点已成功记录正常入库。
   验收：让站点 C 前两次返回 500、第三次成功，断言最终采集完整且该页请求次数为 3；让站点 D 所有请求返回 429 或超时，断言采集在配置上限内结束，进程退出码为 2，快照清单 incomplete=true 且受影响站点包含 D；断言站点 D 的部分修订未出现在 complete 快照中，而站点 A 的成功记录已在库中。
8. 实现审计不可篡改校验：每条修订入库时计算链式哈希（前一修订哈希 + 规范化记录字段），提供离线校验命令遍历每条业务键的修订链，检测字段被直接改写、修订被删除或插入；校验失败输出含业务键与失败类型的字符串业务错误码 E_CHAIN_BROKEN，不得输出崩溃堆栈，且校验在单条失败后继续审计其余记录并在报告中汇总。
   验收：正常采集后执行校验命令，退出码为 0；用 SQLite 直接改写某条修订的签署状态字段后再次校验，断言退出码为 3 且 stderr 含该业务键与失败类型；删除某业务键中间一条修订后校验同样失败并报告该键；断言未受影响的业务键校验结果仍被正常纳入报告且不因前一条失败而跳过。
9. 提供可复现的确定性本地站点仿真与端到端测试：测试代码自行启动 http.server 实例、构造分页、重复投递、撤回、更正、慢响应（固定 sleep 时长）与截断响应；时间戳、随机种子固定，端口由系统分配后通过属性回传给测试与采集配置；不得依赖公网或真实站点；测试覆盖并发上限、幂等重跑、恢复、仲裁、校验五个场景，且并发峰值以服务端计数为准。
   验收：在 Windows 上执行 pytest，全部用例通过并在同一环境重复执行 3 次结果一致；测试 teardown 后所有本地服务已关闭且端口可再次绑定；断言并发上限用例的峰值断言数据来源为服务端计数而非客户端自报；断言恢复用例真实触发过一次进程中断而后重启采集。
10. 输出规范化审计报告与退出码约定：采集完成后生成 JSON 报告，包含版本号、各站点抓取页数与请求次数、去重前后条数、仲裁冲突数、重试次数、incomplete 站点列表、快照集合哈希与业务错误码列表；业务错误码为字符串常量（E_SITE_INCOMPLETE、E_CHAIN_BROKEN、E_INTERRUPTED、E_CONFIG_INVALID），进程退出码为整数：0 全部成功、2 数据不完整或中断、3 校验失败、4 配置错误。
   验收：正常采集报告冲突数与构造的冲突记录数一致，退出码 0；仅站点超时场景退出码 2 且报告错误码列表含 E_SITE_INCOMPLETE；故意篡改后执行校验退出码 3 且报告含 E_CHAIN_BROKEN；配置缺少站点基址时退出码 4 且 stderr 输出 E_CONFIG_INVALID。
